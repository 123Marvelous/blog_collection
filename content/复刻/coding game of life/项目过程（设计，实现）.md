### 2. 编译与运行连招 由于引入了第三方 SDL2 图形库，普通编译会报错（找不到头文件/未定义引用）。必须配合环境自动配置工具。

### 3. 🚨 踩坑记录 (远程图形输出困境) 
* **现象**：在 Windows VS Code 的 SSH 终端里运行 `./gol`，程序在后台跑了，但桌面上没有任何反应，按 `Ctrl + Shift + C` 也弹不出窗口。
* **原因（次元壁）**：SSH 连接属于纯文本通道，无法直接将虚拟机（Ubuntu）里运行的图形画面信号传输回 Windows 主机屏幕。
* **解决方案**：保持 SSH 编译，但必须切换到 **VMware 虚拟机的原生图形桌面** 去观察弹出的黑色窗口。

### 4. 💡 终极顿悟：数组传参的“维度丢失”与“地址误解”

#### 📌 核心底层规律
在 C 语言中，数组名作为参数传递时，遵循两条铁律：
1. **传参的本质（扔首地址）**：无论是 `int a[600]` 还是 `int b[20][30]`，传参时编译器都只复制了**内存大门口第一个格子的物理地址**（一串光秃秃的门牌号）扔给函数。
2. **维度丢失**：这个地址在传输过程中**不携带任何维度信息**。这个地址代表什么结构，全看函数接收端（形参）怎么去“解读”。

---

#### 📌 三种形参接收方式的底层物理对比

| 接收端写法 | 计算机的解读方式 | 寻址物理公式 / 行为 | 结果与代价 |
| :--- | :--- | :--- | :--- |
| **`int matrix[rows][columns]`** <br>*(VLA变长数组)* | 认为首地址是一个**二维方阵**。 | `首地址 + i * columns + j`<br>（编译器全自动代入公式算步长） | **🟢 最佳地道写法**。内部可爽快写 `matrix[i][j]`，不爆栈，最安全。 |
| **`int *matrix`** <br>*(一维纯指针)* | 认为首地址是一条**一维直线**。 | `*(matrix + i * columns + j)`<br>（逼迫程序员自己在内部手写降维计算） | **🟡 博主早期写法**。需要人肉算步长，代码可读性差，但参数顺序自由。 |
| **`int **matrix`** <br>*(二级指针)* | 认为首地址是**一个装满“行地址”的指针数组**。 | 拿着首地址 $\rightarrow$ 挖出里面的内容（以为是地址） $\rightarrow$ 再次追踪。 | **❌ 必然报段错误暴毙**。类型完全错配，无法兼容真二维数组。 |

---

#### 📌 🚨 拆解：为什么写 `int**` 必然引发“段错误”？

当强行把真二维数组名字投喂给 `int **matrix` 时，计算机在底层的悲剧流程如下：

```text
 1. 传参：main 扔过去一个物理首地址 (例如: 0x7fff5f)
 
 2. 函数执行 matrix[0][0]：二级指针的导航逻辑启动
 
 3. 第一次挖地址：计算机来到 0x7fff5f，它坚信这里躺着的是“第一行的内存地址”。
 
 4. 偷梁换柱：然而这里其实是连续存储的数据！计算机拔出来的，是你用 rand() % 2 填进去的活细胞数值 【1】。
 
 5. 误入禁区：计算机把这个数值【1】强行当成了下一次导航的绝对地址，试图去访问物理内存 0x00000001。
 
 6. 操作系统内核击杀：爆出「段错误 (Segmentation fault)」，程序当场暴毙。

```
